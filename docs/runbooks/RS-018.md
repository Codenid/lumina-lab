## Reanudar el diagnóstico

Ejecutar desde WSL con la cuenta autorizada y el proyecto explícito. Primero
confirmar la URL y revisión reales:

```bash
gcloud run services describe luminalab-insights-api \
  --project=lumina-lab-513704 --region=us-central1 \
  --format='yaml(status.url,status.latestReadyRevisionName,status.conditions)'
gcloud run services get-iam-policy luminalab-insights-api \
  --project=lumina-lab-513704 --region=us-central1
```

Luego probar `GET /healthz` con un token de identidad de la cuenta autorizada
y la URL que devolvió `describe`:

```bash
URL="$(gcloud run services describe luminalab-insights-api \
  --project=lumina-lab-513704 --region=us-central1 --format='value(status.url)')"
TOKEN="$(gcloud auth print-identity-token)"
curl -i -H "Authorization: Bearer $TOKEN" "$URL/healthz"
```

Si el resultado no es HTTP 200, guardar la respuesta exacta y revisar logs de
la revisión. La ausencia de logs de solicitud indica que la petición no fue
observada en el contenedor; no demuestra por sí sola si el origen está en DNS,
proxy, frontend o URL:

```bash
gcloud logging read \
  'resource.type="cloud_run_revision" AND resource.labels.service_name="luminalab-insights-api" AND resource.labels.revision_name="luminalab-insights-api-ra77c199111"' \
  --project=lumina-lab-513704 --limit=100 --format=json
```

Cuando `/healthz` responda 200, ejecutar de nuevo el script 66. Este hace una
sola llamada por ruta y verifica que las cuatro rutas de negocio devuelvan
datos; después ejecutar 67 para actualizar la evidencia. No marcar RS-018 como
completo hasta que el script 66 sea 1.
